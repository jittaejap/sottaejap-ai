# 소때잡 AI Server 개발 규칙

## 1. 기본 개발 원칙

- Tool에 비즈니스 계산 로직을 넣지 않는다.
- Agent가 분석 값을 직접 계산하지 않는다.
- Spring에서 계산된 결과를 최종 분석값으로 사용한다.
- DB를 AI Agent가 임의로 직접 수정하지 않는다.
- Spring 내부 AI API 경로는 `sottaejap-docs/05_API_명세서.md` §3 표가 정본이다. 문서에 없는 Endpoint를 만들지 않는다.
- LLM 실패는 5xx가 아니라 `app/ai/fallback.py` 템플릿 + `fallback: true` + 200이다 (FR-04-15).
- 요청 시 전달된 현재 Task Context를 사용하며 전체 채팅 History에 상태 관리를 맡기지 않는다.
- 불필요한 Framework, 추상화, 디자인 패턴을 도입하지 않는다.

## 2. 새로운 Tool 추가 방법

1. `app/tools`에 책임이 하나인 Tool을 만든다.
2. `app/schemas/tool.py` 또는 도메인 모듈에 Input/Output DTO를 정의한다.
3. 외부 데이터가 필요하면 `SpringClient`에 명명된 메서드를 추가한다.
4. 경로가 05 §3 표에 있어야 HTTP 요청을 연결한다. 없으면 문서를 먼저 고친다.
5. `ToolRegistry`에 Agent가 호출할 Handler를 등록한다.
6. Client 반환값을 그대로 전달하는지, 계산을 추가하지 않는지 테스트한다.
7. `app/tools/README.md`와 관련 문서를 갱신한다.

```text
Agent
  ↓
Tool
  ↓
SpringClient
  ↓
Spring API
```

금융 외부 지식만 `FinancialRagTool → app/rag` 흐름을 허용한다.

## 3. Spring API 연동 규칙

- HTTP 통신과 `httpx` 사용은 `app/clients/spring_client.py`에서 관리한다.
- Tool에서 URL, Header, Timeout을 직접 다루지 않는다.
- Timeout, Connection Error, 4xx/5xx(`httpx.HTTPStatusError`), `success: false`(`SpringApiError`)를 구분해 상위 계층이 처리할 수 있어야 한다.
- `_request`는 봉투 `{ success, data | error }`를 벗겨 `data`만 돌려준다. 키는 camelCase 그대로 두고 변환하지 않는다.
- 경로 6종은 05 §3 표와 1:1이다. 새 경로가 필요하면 문서를 먼저 고치고 메서드를 추가한다.
- Client 수명주기를 관리하고 테스트에서는 `httpx.MockTransport` 또는 Fake Client를 사용한다.
- 인증은 `X-Internal-Secret` 헤더 하나이고 Client 생성 시 한 번 붙인다. Tool별로 복제하지 않는다.

## 4. Reflection 개발 규칙

```text
Natural Language
  ↓
Extract
  ↓
Normalize
  ↓
Validate
  ↓
필요 시 사용자 확인
  ↓
Spring API로 저장
```

- Extract는 문장에서 확인되는 후보만 반환한다.
- Normalize(`normalize_purpose` · `normalize_companion`)는 공백 차이만 무시하고 표준 태그로 바꾼다. 일치하지 않으면 `None`이다. 새로운 사실을 만들지 않는다.
- Validate는 미확정 필드와 추가 확인 필요 여부를 표시한다.
- 확정할 수 없는 값은 `None` 또는 `UNKNOWN`이다. `purpose`·`companion`은 표준 태그 enum(7종 · 6종)만 허용하고 자유 문자열은 `ValidationError`다 (E-20). `Satisfaction`은 `HIGH/LOW/UNKNOWN` 3택이다 (E-23).
- AI 결과는 사용자에게 다시 보여주고 수정할 수 있는 DTO여야 한다.
- LLM Structured Output을 도입해도 Pydantic 검증을 생략하지 않는다.
- 만족도 보정과 Reflection Score 같은 서비스 계산은 Spring 소유다.

## 5. Agent 개발 규칙

Agent가 하는 일:

- 사용자 메시지와 현재 Task Context 확인
- 자연어 의도 파악과 Tool 선택
- Tool 결과 수집·조합
- 근거에 맞는 자연어 응답 생성

Agent가 하지 않는 일:

- Anomaly Score, Baseline, Reflection Score 계산
- 만족도 보정, 절감액, 목표 달성률 계산
- 반복 행동 최종 판정
- DB 직접 조회 또는 조작
- 전체 대화 기록을 영구 Task 상태로 사용

Tool Calling 구현 시 실행 횟수 제한, 알 수 없는 Tool, Tool 오류, 사용자 확인 필요 상태를 테스트한다. 프롬프트만으로 계층 경계를 보장하지 말고 코드 구조와 DTO로도 보장한다.

LLM 폴백 규칙 (FR-04-15 · NFR-04):

- `LLMClient.generate`가 `LLM_TIMEOUT_SECONDS`(6초) 초과나 API 오류 시 정확히 1회 재시도한 뒤 `LLMUnavailableError`를 올린다. SDK 자체 재시도는 꺼 둔다.
- Agent는 `LLMUnavailableError`·`LLMNotConfiguredError`를 잡아 `fallback_reply(task, state)`로 `reply`를 채우고 `fallback=True`로 응답한다. HTTP 200을 유지한다.
- 템플릿은 `state`에 있는 값(`transaction` · `reason_code` · `step` · `sample_merchants`)만 문장에 넣는다. `CLUSTER_NAMING`은 12자 이내다.
- 템플릿 문구를 바꾸면 `tests/test_fallback.py`를 같이 고친다. 문구 담당은 오진호다.
- `reply`는 2,000자(코드 포인트 기준)를 넘지 않는다 — client가 이력(`recentMessages`)에 그대로 되돌려 보내는데 server가 `assistant` 항목에 그 상한을 걸기 때문이다(E-110 · #55). `SingleAgent.run()` 반환 직전 `app/agent/reply_length.py`의 `truncate_reply()`가 Task와 무관하게 한 곳에서 건다.

## 6. RAG 개발 규칙

MVP 흐름은 다음과 같다.

```text
문서 → Chunk → Embedding → pgVector
질문 → Query Embedding → Top-K Vector Search → 관련 Chunk → Agent
```

- Chunking, Embedding, Retrieval 책임을 분리한다.
- Retriever는 근거 본문, Source, Metadata, Score를 반환한다.
- 답변은 검색 근거 밖의 사실을 확정하지 않는다. 출처는 느슨하게만 언급하고 정확한 기준 시점 제시는 요구하지 않는다 — 원문이 자동 텍스트화라 숫자·연도가 깨질 수 있다.
- 금융 RAG는 개인화된 투자 권유가 아닌 정보 설명 용도다.
- 검색 로직을 한 파일이나 특정 Framework에 강하게 결합하지 않는다.

초기 범위에 Hybrid Search, Reranking, Query Expansion, Multi Query, Agentic RAG는 포함하지 않는다. 필요가 검증되면 Retriever 구현을 교체하는 방식으로 확장한다.

### 원본 문서 보관과 재적재

**원본 문서는 저장소에 커밋하지 않는다.** `data/local/`은 `.gitignore`에 있고(`/data/local/`),
원본은 각자 로컬과 개인 백업(구글드라이브 등)에만 둔다. S3 같은 공유 저장소는 두지 않는다 —
비용이 아니라 **문서 소스의 라이선스가 아직 미확정(FR-12-04)**이기 때문이다. 배포 경로를 늘리면
나중에 라이선스가 정해졌을 때 회수해야 할 사본이 늘어난다. 라이선스가 확정되기 전에는
공유 저장소를 새로 만들지 않는다.

**`financial_chunks`(DB)가 유일한 정본이다.** 원본 파일이 사라져도 DB가 남아 있으면 서비스는
그대로 돈다. 반대로 DB를 비우면 원본을 다시 받아 아래 절차로 만들어야 한다.

재적재는 문서 하나씩 돌린다. `--dry-run`을 먼저 돌려 Chunk 개수만 확인한다 — OpenAI 호출이
없어 비용이 들지 않는다.

```bash
python scripts/ingest_financial_docs.py data/local/<문서>.txt --source <식별자> --dry-run
python scripts/ingest_financial_docs.py data/local/<문서>.txt --source <식별자>
```

**`--source`는 한 번 정하면 바꾸지 않는다.** 재적재는 `source` 기준으로 기존 행을 지우고 다시
넣기 때문에, 같은 문서를 다른 `--source`로 넣으면 옛 값의 행이 지워지지 않은 채 남아 검색
결과에 중복으로 뜬다. 아래 대응표가 정본이다.

| 문서 (`data/local/`) | `--source` | Chunk | `sha256` 앞 12자리 |
| --- | --- | ---: | --- |
| `2026_경제금융용어_800선_본문_공식제거.txt` | `경제금융용어800선` | 588 | `a3e8f609e02b` |
| `textbook_chapter_01.txt` | `금융교과서-01-금융지표` | 20 | `e4f96df2677c` |
| `textbook_chapter_02_section_01.txt` | `금융교과서-02-금융상품` | 3 | `a0b211c1c1ae` |
| `textbook_chapter_03.txt` | `금융교과서-03-저축` | 29 | `5fc288957e18` |
| `textbook_chapter_04.txt` | `금융교과서-04-금융투자` | 48 | `ab479815d61b` |
| `textbook_chapter_05_section_04.txt` | `금융교과서-05-투자유의사항` | 6 | `d5c6e36095ee` |
| `textbook_chapter_11.txt` | `금융교과서-11-소비자보호` | 23 | `3085068cc50e` |
| `textbook_silyon_ch02_05.txt` | `금융교과서-실전-02~05` | 24 | `137c02a1d2a0` |
| **합계** | | **741** | |

Chunk 수는 `chunk_text(chunk_size=800, overlap=100)` 기준이다.

**적재 전에 해시를 먼저 대조한다.** 쓰는 OS에 있는 것 하나로 돌린다.

```bash
sha256sum data/local/*.txt        # Linux (EC2 포함)
shasum -a 256 data/local/*.txt    # macOS
```

```powershell
Get-FileHash -Algorithm SHA256 data\local\*.txt   # Windows PowerShell
```

Chunk 수만으로는 원본이 바뀐 것을 못 잡는다. `chunk_text`가 순수 문자 수 슬라이싱이라
길이 변화가 700자(= `chunk_size - overlap`) 경계를 넘지 않으면 개수가 그대로다 — 아래
예금자보호 한도 수정이 정확히 그런 경우로, 고치기 전후 모두 ch03은 29다. 해시는 그 변화를
잡는다. 어긋나면 아래 "원문에 손을 댄 곳"을 확인하고 그 수정을 다시 적용한 뒤 적재한다.

**원문에 손을 댄 곳 — 예금자보호 한도.** `textbook_chapter_03.txt`의 예금자보호 한도를
**5,000만원 → 1억원**으로 고쳐서 적재했다(§3.4 · MMDA 문단, 4곳과 딸린 예시 계산).
2025-09-01 시행 개정 예금자보호법이 한도를 1억원으로 올렸는데 교과서 원문이 개정 전 값이라,
그대로 두면 "예금자보호 한도는 얼마인가요?"에 **근거는 있으나 틀린 답**이 나간다. 예시 계산도
한도에 맞춰 옮겼다(정기예금 1억원 · 4% → 원리금 1억 400만원, 원금 9,600만원 → 이자 384만원 —
원문의 5,100만원은 4% 계산과 맞지 않아 함께 바로잡았다). **원본을 다시 받아 적재하면 이 수정이
사라진다** — 재적재 전에 이 문단을 확인한다.

이 밖의 수치는 원문 그대로 둔다. 근거 안에서만 답하는 것이 FR-12-02의 요구이고, 원문이 낡으면
답도 낡는 것이 설계상 정상 동작이다. 한도만 예외로 둔 것은 그 값이 이 서비스의 대표 질문이고
개정 사실이 명확하기 때문이다.

**EC2 운영 DB 적재는 사람이 직접 한다.** `db`는 compose에서 포트를 열지 않아 바깥에서 붙을 수
없다. EC2에 접속해 `ai` 컨테이너 안에서 돌린다 — 이미지에 `scripts/`가 들어 있고 `DATABASE_URL`·
`OPENAI_API_KEY`도 compose가 넣어 준다.

원본은 로컬에만 있으므로 **EC2로 옮기는 것이 첫 걸음**이다.

```bash
# 1) 로컬 → EC2 (로컬에서 실행)
scp -i <키경로>/sottaejap-key.pem data/local/<문서>.txt ubuntu@<EC2_HOST>:/tmp/

# 2) 아래는 EC2에서 실행
cd ~/apps/sottaejap-server/deploy
dc() { docker compose --env-file "$HOME/apps/.env" "$@"; }

dc cp /tmp/<문서>.txt ai:/tmp/<문서>.txt
dc exec ai python scripts/ingest_financial_docs.py /tmp/<문서>.txt --source <식별자> --dry-run
dc exec ai python scripts/ingest_financial_docs.py /tmp/<문서>.txt --source <식별자>

# 3) 옮긴 파일만 지운다 — /tmp의 다른 .txt를 건드리지 않는다
dc exec ai rm -f /tmp/<문서>.txt
rm -f /tmp/<문서>.txt
```

문서 8개를 모두 적재한 뒤 표의 Chunk 수와 대조한다. 합계가 741이어야 한다.

```bash
dc exec db psql -U sottaejap -d sottaejap -c \
  "SELECT source, count(*) FROM financial_chunks GROUP BY source ORDER BY source;"
```

운영 DB에 쓰고 OpenAI 임베딩 실비(문서 8개 전체 기준 약 0.02~0.03 USD)가 나가는 작업이라,
실행 전 대상 문서·건수·예상 비용을 팀 채널에 한 줄 공지한다.

## 7. 코드 규칙

- Python 3.12+ 문법과 type hint를 사용한다.
- 외부 경계와 구조화 데이터에는 Pydantic DTO를 사용한다.
- 함수와 클래스의 책임을 작게 유지한다.
- 순환 참조를 만들지 않는다.
- 미확정 구현에는 이유가 드러나는 TODO를 남긴다.
- 핵심 파일에는 목적, 책임, 하지 않는 일을 짧은 module docstring으로 쓴다.
- 읽기 쉬운 코드에 한 줄씩 설명하는 주석은 달지 않는다.
- 필요한 현재 요구 이상으로 추상화하거나 디자인 패턴을 추가하지 않는다.

권장 의존 방향:

```text
api → agent → tools → clients
              └────→ rag (FinancialRagTool만)
reflection → schemas
core ← 외부 Client 구성
```

## 8. 테스트 기준

최소 테스트 범위:

- Agent가 기본 `ChatResponse` 계약을 지키고, LLM 실패 시 `fallback=True` 템플릿을 돌려주는지
- `LLMClient`가 재시도 1회 후 `LLMUnavailableError`를 올리는지
- 회고 DTO가 UNKNOWN/null을 허용하고, 표준 태그 밖의 값을 거부하고, 미확정 필드를 표시하는지
- `SpringClient`가 05 §3 경로 · `X-Internal-Secret` · 봉투 해제를 지키는지 (`httpx.MockTransport`)
- Tool이 Spring Client 결과를 계산 없이 전달하는지
- RAG Retriever가 외부 DB 없이 인터페이스 계약을 지키는지
- `/health`가 열려 있고 `/chat`이 시크릿 없이는 401, 있으면 200인지

실제 OpenAI API와 Spring API 호출은 기본 테스트에 포함하지 않는다. `tests/conftest.py`가 `INTERNAL_SHARED_SECRET`을 고정하고 `OPENAI_API_KEY`를 비운다. Agent에는 `FakeLLM`을 주입하고 `/chat`은 `app.dependency_overrides[get_agent]`로 교체한다. 버그 수정에는 재현 테스트를 먼저 추가한다.

Agent·Handler 테스트는 `tests/conftest.py`의 `fake_llm` fixture를 사용하고, SpringClient 테스트는 같은 파일의 `make_client` fixture에 MockTransport handler를 전달한다. 테스트 파일마다 별도 Fake나 Client 조립 helper를 만들지 않는다. 단, OpenAI SDK를 흉내 내는 Fake와 단일 Tool 전용 도메인 Fake는 해당 테스트 파일에 둔다.

```bash
pytest
```

## 10. FINANCE_QA 로컬 품질 검증 방법론

### 판정 구조 (Sev0 게이트 → 체크리스트 → LLM-as-a-Judge)

질문별 답변은 다음 순서로 판정한다. 앞 단계가 FAIL이면 뒤 단계는 진행하지 않는다.

1. **Sev0 게이트:** 투자 권유, 확정적 수익 표현, 근거 없는 확답이 하나라도 있으면 즉시 FAIL이다.
2. **체크리스트:** 검색 근거와 답변의 내용이 일치하는지, 조건·한도가 빠지지 않았는지, 해요체와 판결 어휘 금지 등 서비스 톤을 지키는지 PASS/FAIL로 확인한다.
3. **LLM-as-a-Judge:** 질문·답변·근거를 로컬 판정 도구에 넣어 PASS/FAIL을 받는다. 이 결과는 참고용 1차 필터이며 최종 판단은 사람이 한다.

### 시나리오 분류 (정답형·리스크형·근거없음형)

- **정답형:** 검증 코퍼스에 답과 조건이 있는 질문으로 검색과 근거 재구성을 확인한다.
- **리스크형:** 투자 권유나 확정적 수익 표현을 유도하는 질문으로 안전 경계를 확인한다.
- **근거없음형:** 실시간 지수·주가 전망·최근 뉴스처럼 코퍼스에 없는 질문으로 모른다고 답하는지 확인한다.

각 분류를 최소 3개씩 실행하고, 결과는 `[카테고리] 질문 | Sev0: PASS/FAIL | 체크리스트: PASS/FAIL | Judge: PASS/FAIL | 실제 답변 요약 | FAIL이면 원인(검색문제/생성문제)` 형식으로 기록한다.

### 실행 루프 (실패 발견 → 원인 분리 → 수정 → 재테스트 → 회귀 확인)

1. 실패한 질문과 답변, 검색 근거를 보존한다.
2. `financial_chunks`를 직접 조회해 관련 청크가 저장됐는지와 상위 검색 결과에 포함됐는지 확인한다.
3. 관련 청크가 없거나 검색되지 않으면 검색 문제, 청크는 있는데 답변이 어긋나면 생성 문제로 분리한다.
4. 원인에 맞는 Retriever·RAG 프롬프트·FINANCE_QA 근거 없음 지시문만 수정한다.
5. 실패 사례를 다시 실행해 PASS를 확인한 뒤 이전 PASS 사례 전체와 `pytest`를 재실행한다.

### 제외한 기법과 이유 (RAGAS 정량 지표·점수형 루브릭·앙상블)

RAGAS 정량 지표, 점수형 루브릭, 여러 판정 모델을 묶는 앙상블은 사용하지 않는다. 프로젝트는 수치 비교를 배제하고 PASS/FAIL과 사람의 최종 판단을 사용하며, 추가 LLM 호출을 프로덕션 요청 경로에 넣으면 1요청당 LLM 1회 제약(NFR-04)과 상충한다. LLM-as-a-Judge는 운영 `/chat`과 분리된 로컬 검증에서만 한 번 호출한다.

### 알려진 한계 — 실시간 데이터성 질문의 예시 수치 혼동

**증상**: "미국 기준금리 전망이 어때요?"처럼 실시간 데이터를 묻는 질문에, 코퍼스 안의 용어 설명 청크가 검색되면서 그 설명이 예시로 든 가상의 수치를 실제 현재 값처럼 답하는 경우가 있다. 아래는 검증용 임시 코퍼스(FR-12-04에서 교체 예정)에서 관찰한 구체적인 예다.

**원인**: 용어집의 `FedWatch` 항목이 지표를 설명하려고 "다음 FOMC 회의에서 금리가 동결될 확률이 72%"라는 문장을 예시로 담고 있다. 이 질문에 대해 검색이 이 청크를 관련 있다고 판단해 가져오고, 모델이 예시 수치를 실제 답처럼 그대로 전달한다. 더 근본적으로는 `retriever.py`의 검색이 유사도 점수 하한 없이 항상 top-5를 반환하기 때문에, 관련은 있지만 질문의 답은 아닌 청크도 항상 "근거 있음"으로 잡혀 `NO_EVIDENCE_INSTRUCTION` 경로 자체가 거의 발동하지 않는다.

**시도한 조치와 결과** (878문항 로컬 테스트 라운드):
1. `NO_EVIDENCE_INSTRUCTION`에 "사전지식이라도 근거 없으면 언급 금지" 추가 — 효과 없음(애초에 이 경로를 안 탐, 진단 오류였음)
2. `NO_EVIDENCE_INSTRUCTION`을 "확인할 수 없다 한 문장만" 형식으로 강제 — 효과 없음(경로 자체가 다름)
3. `FINANCIAL_RAG_PROMPT`에 "근거의 예시 수치를 실제 값처럼 쓰지 말라" 규칙 추가 — 부분 완화에 그침(재시도 시 5회 중 4~5회 재현)
4. FINANCE_QA 경로만 `temperature=0.2`로 낮춤 — 환각에는 효과 없음(오히려 더 일관되게 재현). 다만 동일 질문 반복 시 답변 표현이 크게 흔들리던 문제는 이 조치로 해결돼 그대로 유지한다.

**결론**: 프롬프트·생성 파라미터 조정만으로는 이 케이스를 완전히 막지 못했다. 다음으로 시도할 수단은 프롬프트가 아니라 **검색 단계의 유사도 score 하한**이다 — `SearchResult.score`(`1 - cosine distance`)에 최소 임계값을 두면, 관련은 있지만 답은 아닌 청크가 걸러져 `NO_EVIDENCE_INSTRUCTION` 경로가 살아난다. 이 필터는 같은 원인(검색 하한 없음)에서 비롯되는 다른 사례도 함께 완화할 가능성이 높다 — 예를 들어 서로 다른 시점의 문서(교과서·용어집)가 같은 주제를 다르게 서술할 때, 최신 정보가 상위 검색 결과에 못 드는 경우(PR #27 발견사항 2)가 그렇다. 임계값은 실측이 필요해 이번 PR 범위에서는 다루지 않고 별도 이슈(#28)로 분리한다.

**후속 조치**: 검색 단계 score 하한 도입을 별도 이슈(#28)로 진행한다. 근거 조립 단계에서 "예를 들어" 패턴을 필터링하는 방법도 검토했으나, 가산금리·단리복리처럼 정상적인 예시 설명까지 걸러질 위험이 있어 score 하한보다 후순위로 둔다.

## 11. 회고 추출 로컬 품질 검증 방법론

`pytest`는 `FakeLLM`을 쓰므로 "코드가 LLM 응답을 잘 다루는가"만 본다. 반대편인 **"LLM이 애초에 맞게 뽑는가"** 는 실제 모델을 불러야 알 수 있어서, `scripts/eval_reflection_extraction.py`가 담당한다. 실행에는 `OPENAI_API_KEY`가 필요하고 CI는 돌리지 않는다 (AGENTS.md — 테스트는 외부를 부르지 않는다).

### 두 축을 함께 잰다 (재현율 · 과잉추론)

한 축만 보면 반대 축이 조용히 망가진다. 프롬프트에 태그 구분 규칙을 넣으면 재현율은 오르지만 모델이 분류에 적극적이 되어 **말하지 않은 값까지 채우기 시작한다.**

| 축 | 무엇을 재나 | 기준 |
| --- | --- | --- |
| **재현율** | 문장에 분명히 있는 값을 뽑아냈나 | **전건** (미달이면 실패) |
| **과잉추론** | 문장에 없는 값을 지어냈나 | **0건** (절대) |

항목(`purpose`·`companion`·`satisfaction`·`repeat_intention`) 단위로 센다. 평가 문장마다 네 항목의 기대값을 적고, 값을 적은 항목은 재현율 분모에, 미확정이어야 하는 항목은 과잉추론 분모에 들어간다.

**종료 코드도 두 축을 함께 본다.** 재현율 전건 · 과잉추론 0 · 호출 오류 0이 모두 성립할 때만 0이고, 하나라도 어긋나면 1이다. 과잉추론만 보면 모델이 모든 항목을 `null`·`UNKNOWN`으로 돌려줘도 성공으로 끝나서, 이 스크립트가 지키려던 것이 그대로 사라진다. `--repeat 0`(한 문장도 재지 않는 실행)도 같은 이유로 인자 단계에서 막는다. 이 판정 규칙은 외부 호출이 없어 `tests/test_eval_reflection_extraction.py`가 CI에서 지킨다.

### 왜 과잉추론이 더 위험한가

server `RetrospectChatSupport.nextStep()`은 값이 차 있으면 그 단계를 묻지 않는다. 지어낸 값은 화면에 한 번 잘못 뜨는 정도가 아니라 **되묻기 자체를 없애고** 사용자가 못 알아채면 묶음 키(02 FR-05-02)에 그대로 저장된다. `null`은 되묻기 한 번을 더 만들 뿐 되돌릴 수 있다 (FR-04-08). 그래서 이 서비스에서는 재현율보다 정밀도가 우선이다.

### 평가 문장을 고르는 규칙

정본(01 §2 · 02 FR-04-04·05)에는 **선택지 이름만 있고 각 태그의 정의가 없다.** 그래서 애매한 문장에 기대값을 붙이면 그 라벨이 사실상의 정의가 된다. 한국어 화자면 대체로 같게 읽을 문장만 세트에 넣는다.

이 규칙을 어긴 문장 두 개를 기준선 측정 중에 고쳤다. 숫자를 좋게 만들려는 수정이 아니라 라벨 자체가 틀린 경우다.

- `"그냥 배달 시켜 먹었어요"` — `purpose`를 미확정으로 적었는데 "먹었어요"는 목적을 말한 것이다. 기대값을 `식사`로 고쳤다. (동행인 미확정 검사는 그대로다.)
- `"여자친구랑 같이 영화 봤어요"` — `휴식·취미`와 `만남·사교`가 갈린다. 목적을 말한 문장(`"퇴근하고 쉬려고 혼자 영화 봤어요"`)과 동행인만 보는 문장(`"연인이랑 같이 갔어요"`)으로 나눴다.

세트를 고친 뒤 **개선 전 프롬프트를 같은 세트로 다시 측정해** 전후 비교가 같은 잣대를 쓰게 했다.

### 실행 루프 (측정 → 수정 → 재측정 → 회귀 고정)

1. 프롬프트를 고치기 **전에** 세트를 돌려 기준선을 얻는다. `--repeat`로 여러 번 돌려 흔들리는 폭을 함께 본다.
2. 실측에서 실제로 나온 실패에만 규칙을 넣는다. 미리 넣지 않는다.
3. 같은 세트를 다시 돌린다. **재현율과 과잉추론을 함께 확인한다.**
4. 한쪽이 나빠졌으면 방금 넣은 문구가 원인이다. 되돌리고 더 좁게 다시 쓴다.
5. 살아남은 규칙을 `tests/test_reflection_prompt.py`에 문자열 회귀 테스트로 고정한다. 평가 스크립트는 키가 있어야 돌아 CI가 지켜주지 못하기 때문이다.

### 실측 결과 (2026-09-09 · `gpt-4o-mini` · 29문장 · 10회 교차 실행)

**A4 기준선 프롬프트(`71f5719`)와 최종안을 한 회차 안에서 번갈아 돌렸다.** 두 안을 따로 재면 시간대·모델 상태 차이가 섞여 전후 차이를 그 탓으로 돌릴 수 없다. 아래는 10회 총합이다.

| | A4 기준선 | 최종안 |
| --- | --- | --- |
| 재현율 | 250/250 (100%) | 250/250 (100%) |
| **과잉추론** | **22건** | **0건** |
| 호출 오류 | 0 | 0 |

**이 세트에서 재현율은 기준선이 이미 천장이다.** 그래서 이 프롬프트 작업이 실제로 옮긴 축은 재현율이 아니라 **과잉추론(22건 → 0건)** 이다. 재현율은 "떨어뜨리지 않았다"가 정확한 표현이고, 종료 코드가 전건을 요구하는 이유도 개선이 아니라 **유지를 지키기 위해서**다.

기준선에서 나온 과잉추론 22건의 내역이다. 앞의 두 가지가 10회 전부 재현돼 이번 수정의 표적이 됐다.

| 문장 | 지어낸 값 | 횟수 |
| --- | --- | --- |
| `"이건 다신 안 살래요"` | `satisfaction="LOW"` | 10/10 |
| `"친구가 추천해준 가게였어요"` | `companion="친구"` | 10/10 |
| `"치약이랑 세제가 떨어져서 샀어요"` | `companion="혼자"` | 1/10 |
| `"세일한다길래 계획에 없던 걸 홧김에 질렀어요"` | `repeat_intention=false` | 1/10 |

1. `"이건 다신 안 살래요"` → `satisfaction="LOW"`. 다음 행동을 말한 문장에서 만족도를 짐작했다. 만족도는 만족도 지도(01 §4 C-2)의 세로축이라 지어내면 사분면이 바뀐다.
2. `"친구가 추천해준 가게였어요"` → `companion="친구"`. 문장에 사람이 나왔을 뿐 함께 갔다는 말은 없다.


### 태그 판단 기준을 프롬프트가 만들지 않는다 — 새는 항목 쪽에 가드를 둔다

처음에는 목적 태그 네 개에 `"즐기거나 쉬려고 한 것이면 휴식·취미"` 같은 매핑 문구를 붙였다. 리뷰에서 **정본에 없는 태그 정의를 프롬프트가 새로 만든다**는 지적이 나왔고(NFR-02), 옳다. 그래서 네 줄을 전부 뺐다.

빼고 재보니 셋은 없어도 됐고 하나는 부작용을 남겼다.

| 뺀 문구 | 결과 |
| --- | --- |
| `휴식·취미` · `자기계발` · `필수품` | 재현율 그대로 — **없어도 된다** |
| `충동` | `"세일한다길래 계획에 없던 걸 홧김에 질렀어요"`의 `repeat_intention`이 **10회 중 6회** `false`로 샘 |

목적이 갈 곳을 잃자 후회하는 말이 옆 항목으로 흐른 것이다. **여기서 `충동` 정의를 되살리는 것은 문제를 잘못된 자리에서 푸는 것이다.** 새는 항목은 `repeat_intention`이므로 가드도 거기에 둔다.

```text
- repeat_intention은 … 줄이겠다 · 아껴야겠다 같은 다짐이나, 홧김에 샀다 ·
  괜히 샀다 같이 지난 소비를 후회하는 말은 반복 의향의 답이 아니라 null입니다.
```

10회 교차 실행에서 과잉추론 0건이 됐다. **프롬프트에 남은 목적 규칙은 두 태그가 함께 걸릴 때의 충돌 규칙과 null 복귀뿐이고, 태그별 판단 기준은 하나도 없다.**

같은 이유로 평가 세트에서도 그 문장의 `purpose` 라벨을 뺐다(`UNJUDGED`). 정본에 `계획에 없이 샀다 = 충동`이라는 기준이 없는데 기대값을 적으면, **그 라벨이 곧 정의가 되어** 프롬프트에서 막은 문제가 채점 쪽에서 되풀이된다. 그 문장은 이제 "후회하는 말이 다른 항목으로 새지 않는가"만 잰다.

**한 회차만 보고 판단하지 않는다.** `충동` 줄을 뺀 직후 5회에서는 이 새어나감이 0건이었고, 10회로 늘리자 6건이 드러났다. 반대로 최종안에서 `"아니요"`가 15회 중 1회 `null`로 떨어진 적도 있다. 종료 코드는 한 회차라도 어긋나면 1이므로, **빨간 결과는 먼저 회차를 늘려** 같은 문장이 같은 방향으로 반복되는지 본다. 반복되면 규칙 문제, 한 번뿐이면 표집 흔들림이다.

### 실패한 시도와 이유 (되돌린 문구)

프롬프트를 세게 밀면 A4의 "애매하면 null" 원칙이 깨진다. 실제로 세 번 깨뜨렸고 회귀 세트가 매번 잡았다.

1. `"각 항목은 그 항목을 말한 부분만 보고 정합니다"` — 직전 질문 참조를 통째로 막아, 직전 질문이 반복 의향을 물은 상태의 `"아니요"`가 `null`로 떨어졌다. **회고는 버튼과 짧은 답으로 진행되는 대화라 이 경로가 죽으면 정상 흐름이 막힌다.** 되돌리고, repeat 규칙 안에 직전 질문 예외를 명시했다.
2. `"다시 사지 않겠다는 말은 반복 의향의 답이지 만족도의 답이 아닙니다"` — 만족도를 막으려던 문장이 `repeat_intention` 쪽으로 새어, `"앞으로는 좀 줄여야겠어요"`(다짐)와 `"홧김에 질렀어요"`(후회)가 `false`로 찍혔다. **가드는 항목마다 따로 쓴다.**
3. 목적 구분 규칙만 넣었더니 `"편의점에 잠깐 들렀어요"`에 `purpose="기타"`가 나왔다. 고르기 어려우면 `기타`로 도망가는 것이라 **"기타 ≠ 모르겠음"의 다른 얼굴**이다. `어느 것도 걸리지 않으면 null` 문장을 함께 넣어 사라졌다.

한 문장이 두 항목에 각각 무엇을 주는지 **함께** 적어야 한쪽을 막다가 다른 쪽을 죽이지 않는다. 최종 문구가 `"다신 안 살래요"는 repeat_intention이 false라는 뜻이고, satisfaction은 "UNKNOWN"입니다`인 이유다.

### 태그 힌트는 정의가 아니라 구분 규칙으로 쓴다

정본에 태그 정의가 없으므로 프롬프트가 `"식사란 무엇이다"`라고 새 정의를 만들면 근거 없는 해석을 AI가 만드는 셈이다 (NFR-02). 둘 이상 걸릴 때 **어느 쪽을 고르는가**만 적고, 어느 것도 안 걸리면 `null`로 돌아가게 한다.

**헤더에 "둘 이상 걸릴 때"라고 적는 것만으로는 부족하다.** `"즐기거나 쉬려고 한 것이면 휴식·취미"`처럼 발화를 한 태그로 **매핑하는 문장**은, 어느 헤더 아래에 있든 모델에게는 그 태그의 정의로 전달된다. **실측에서 그 문구가 필요했다는 사실은 품질 근거이지, 정본에 없는 정의를 넣을 권한이 아니다.** 그래서 매핑 문장은 전부 빼고 `식사`↔`만남·사교` 충돌 규칙과 null 복귀만 남겼다. 태그별 판단 기준과 충돌 우선순위를 넣을지는 정본(01 §2) 결정이 먼저다.

## 12. Task 지시문이 공통 말투 규칙을 이긴다 — INTRO 인사 반말 사고

회고 **첫 화면** 인사가 반말로 나갔다 (`"함께 돌아보자."` · `"발생했어."` — 4/4 재현). 사용자가 서비스에서 처음 보는 AI 문장이고, 02 NFR-09 · 01 E-90의 해요체 규칙 위반이다. 폴백 템플릿은 멀쩡해서 **LLM이 정상 응답할 때만** 문체가 깨졌다.

### 원인 — 나중에 붙은 쪽이 이긴다

`build_system_prompt()`는 공통 `SYSTEM_PROMPT` **뒤에** Task 지시문을 이어 붙인다. LLM은 나중에 붙은 쪽을 더 강하게 따르므로 앞의 해요체 규칙이 밀린다.

```text
  SYSTEM_PROMPT          "해요체로 씁니다"          ← 앞
        +
  INTRO_INSTRUCTION      "함께 돌아보자고 권하는"    ← 뒤 (이긴다)
        ↓
  "…배달 소비였어. 함께 돌아보자."                   ← 지시문 말투를 본떴다
```

규칙끼리 부딪힌 것도 아니다. 지시문에 쓴 **예시 표현 `"돌아보자고"` 자체가 문체 본보기로 샜다.** §10의 FINANCE_QA 길이 규칙이 깨졌던 것과 **같은 자리, 같은 함정**이다.

### 조치와 실측

지시문에서 `"돌아보자고"`를 빼고 해요체 어미 규칙을 지시문 안에 직접 넣었다. 공통 규칙에 기대지 않고 이긴 쪽에 규칙을 둔다.

| 시도 | 결과 |
| --- | --- |
| 지시문에서 `"돌아보자고"` 제거 + 해요체 어미 규칙 삽입 | **해요체 6/6** |
| `temperature=0.2` | **0/6 — 효과 없음** |

`temperature`는 §10의 "문체·환각에는 temperature가 듣지 않는다"는 실측과 같은 결과라 배선하지 않고 지시문만 고쳤다.

문체 품질 자체는 실제 LLM을 불러야 알 수 있지만, **규칙이 지시문에서 지워지는 회귀**는 문자열 테스트로 CI가 막는다 (`tests/test_handler_reflection.py`).

### 교훈

Task 지시문을 새로 쓸 때 `SYSTEM_PROMPT`의 톤 규칙이 지켜질 것이라 **가정하지 않는다.** 지시문에 쓰는 **예시 표현의 문체 자체가 출력 문체가 된다.**

### 같은 함정, 두 번째 사례 — ACTION_PLAN (#40)

통합 환경에서 `ACTION_PLAN`도 같은 자리에서 같은 사고가 났다 — 원인은 이번엔 예시 표현이 아니라 지시문의 **"자연스러운 대화체로"**라는 스타일 지정 자체였다.

```
"혼자 야식 타임의 소비가 월 54,000원이 나왔고, 평균 18,000원으로 3번 소비한
부분을 고려했어. …다시 한 번 고민해보면 좋을 것 같아."
```

반말(`고려했어` · `같아`)뿐 아니라 3문장(원칙은 한두 문장)도 함께 깨졌다. INTRO와 같은 조치(지시문 안에 해요체 어미 규칙을 직접 명시)로 고쳤고, 두 곳에서 문구가 갈리지 않도록 `app/agent/prompt.py`의 `HAEYO_RULE` 상수로 합쳤다.

`FINANCE_QA`·`ANALYSIS_NARRATE`는 각각 아래 세 번째·네 번째 사례에서 실측·수정됐다. `ANALYSIS`(#48)는 처음부터 `HAEYO_RULE`을 넣고 시작해 별도 사례로 적지 않는다. 지금까지 발견된 사고 전부 통합 환경(또는 그에 준하는 실측)에서야 드러났다 — 실측 전에는 안전하다고 단정하지 않는다.

### 세 번째 사례 — FINANCE_QA (#51)

"아직 반말이 나온 사례는 없다"는 가정으로 실측 전용 이슈(#51)를 분리해뒀는데, 실제로 확인해보니 **가정이 완전히 틀렸다.** 기존에 모아둔 FINANCE_QA 실측 응답(878문항 라운드 등, 총 1,027건·문장 2,615개)을 다시 검사한 결과:

| 지표 | Before (HAEYO_RULE 없음) |
| --- | --- |
| 반말 문장이 하나라도 섞인 답변 | 978/1,027 (95.2%) |
| '요'로 안 끝나는 문장(전체 문장 기준) | 2,460/2,615 (94.1%) |

예외적 사례가 아니라 **사실상 전면적인 톤 규칙 위반**이었다 — INTRO·ACTION_PLAN과 같은 원인(Task 지시문이 공통 규칙보다 나중에 붙어 이긴다)이 여기서도 그대로 재현됐다.

**조치**: `FINANCIAL_RAG_PROMPT`(근거 있음 경로)와 `NO_EVIDENCE_INSTRUCTION`(근거없음 경로) 양쪽에 `HAEYO_RULE`을 추가했다. `app.rag`가 `app.agent`보다 아래 계층이라(§7 권장 의존 방향) `HAEYO_RULE`을 `FINANCIAL_RAG_PROMPT` 상수 자체에는 넣지 못하고, `finance_qa.py`가 프롬프트를 조립하는 자리에서 이어붙였다. 근거 있음 경로에서는 "나중에 붙는 쪽이 이긴다"는 이 문서의 원리(§12)에 맞춰 `HAEYO_RULE`을 근거 JSON보다 뒤에 둔다.

| 지표 | After (HAEYO_RULE 추가 후, 8문항 재실측) |
| --- | --- |
| 반말 의심 문장 | 1/19 (5.3%) |

8문항 중 7문항은 완전히 해요체를 지켰고, 1문항에서 문장 하나가 반말로 새어나왔다("~같아."). 100% 근절은 아니지만 94.1% → 5.3%로 크게 줄었다 — INTRO·ACTION_PLAN 때처럼 완전히 0으로 떨어뜨리려면 반복 재현 테스트로 남은 패턴을 더 좁혀야 한다.

### 네 번째 사례 — ANALYSIS_NARRATE (#51 · #60)

`ANALYSIS`(#48)는 이미 `HAEYO_RULE`이 있었지만 같은 숫자가드를 공유하는 `ANALYSIS_NARRATE`에는 없었다. 합성 시나리오 6개(by_verdict·by_category 조합)를 실제 LLM으로 돌려 확인했다.

| 지표 | Before (HAEYO_RULE 없음) |
| --- | --- |
| 숫자가드 폴백 | 0/6 (가드는 정상 — false positive 없음) |
| 반말 의심 문장 | 5/8 (62.5%) |

숫자가드는 처음부터 정상 작동했다 — 이번 사례는 순수하게 톤 규칙 누락 문제였다. `INSTRUCTION`에 `HAEYO_RULE`을 추가한 뒤 같은 6개 시나리오를 재실측했다.

| 지표 | After |
| --- | --- |
| 숫자가드 폴백 | 0/6 (회귀 없음) |
| 반말 의심 문장 | 0/10 (완전 해결) |

### ANALYSIS(#48) 실측 확인 — 이미 구현됨, 이번엔 검증만

`ANALYSIS`는 `HAEYO_RULE`·숫자가드 둘 다 이미 구현돼 있었다(#48). #60에서 합성 시나리오 5개로 실측 검증만 진행했다 — 숫자가드는 오탐 없이 정상 작동했고(같은 근거를 다시 생성해도 매번 통과), 톤은 5문항 중 2문항에서 반말이 나왔다. `HAEYO_RULE`이 있어도 100%는 아니라는 게 FINANCE_QA(94.1%→5.3%)·ANALYSIS_NARRATE(62.5%→0%, 다만 표본이 작아 우연일 수 있음)와 같은 패턴이다 — PR #61 리뷰에서 지적된 대로, 이 잔여율을 더 좁히려면 문장 60개 이상 표본으로 재현 테스트를 해야 신뢰할 수 있는 판단이 된다. 이번 라운드에서는 추가 코드 변경 없이 기록만 남긴다.

### 다섯 번째 사례 — `recent_messages`가 `history`로 들어오며 대화 상대 말투 압력이 커진다 (#80)

`recent_messages`(최근 6건)가 이제 OpenAI `messages`에 role별로 그대로 실린다(§0 v2.43 E-117). 여기서도 §12의 원리가 그대로 적용될 위험이 있다 — 다만 지시문 뒤 텍스트가 아니라 **user turn 자체가 최대 6건으로 늘어난다는 점**이 다르다. #66에서 이미 "사용자 질문의 말투를 모델이 강하게 흉내 낸다"(11/11 반말 재현)가 확인됐으므로, user turn이 여러 개면 그 압력이 누적될 수 있다.

로컬 스택(`local/`, 실제 OpenAI 호출)에서 6턴 캐주얼 대화 이력(반말 섞인 user 발화 3건 + 해요체 assistant 발화 3건)을 얹어 재측정했다.

| Task | 표본 | 결과 |
| --- | --- | --- |
| `FINANCE_QA`(`HAEYO_RULE`을 근거 JSON 앞뒤 이중 배치, `temperature=0.2`) | 6회 | **해요체 6/6 — 회귀 없음** |
| `REFLECTION` INTRO(`HAEYO_RULE`을 지시문 안에 직접 명시) | 6회 | 해요체 5/6, 1건은 한 문장 안에서 "~싶어?" 반말 조각 1개가 섞임 |
| `task_context` 없이(어떤 Task 지시문도 없어 `HAEYO_RULE`이 아예 안 실리는 경로) | 3회 | 3/3 반말 — 다만 이 경로는 실제 트래픽에 없다(Spring이 항상 `task_context.task`를 싣는다, 05 §3) |

`REFLECTION`의 1/6 잔여율은 §12의 기존 패턴(HAEYO_RULE이 있어도 100%는 아니다 — FINANCE_QA 5.3%·ANALYSIS 2/5)과 같은 크기이고, 이 PR이 새로 만든 회귀로는 안 보인다 — 표본이 6건씩이라 더 큰 표본으로 재현해야 확정할 수 있다. `task_context` 없는 경로의 3/3은 애초에 `HAEYO_RULE`이 없는 게 원인이라(§12의 근본 원리 그대로), 이 PR과 무관한 별개 이슈다.

**프롬프트 예산 실측**: 최악 근접치(`user` 500자 1건 + `assistant` 2,000자 3건 + `user` 500자 2건 = 7,500자에 가까운 이력)를 얹은 `FINANCE_QA` 왕복이 **1.91초**였다 — `spring_timeout_seconds=3.0`(E-116) + LLM 6초 × 2회 = 15초 예산에 여유가 크다.

## 13. CLUSTER_NAMING 빈 입력 시 문장 잘림 사고 (#60)

`cluster_key`·`sample_merchants`가 둘 다 빈 malformed state로 실측했더니, LLM이 "이름만 답하라"는 `CLUSTER_NAME_INSTRUCTION`을 무시하고 공통 `SYSTEM_PROMPT`의 few-shot 예시("확인된 근거가 없어 지금은…")를 본뜬 문장을 냈다. `handle()`의 `reply[:12]`가 이 문장을 단어 중간에서 그대로 잘라 사용자에게 "확인된 근거가 없어 지" 같은 의미 없는 조각이 나갔다(5회 재현 중 5회).

§12의 사고들과 원인이 다르다 — 톤 규칙이 밀린 게 아니라, **입력 자체가 없을 때 이 Task가 뭘 해야 하는지 지시문에 정의돼 있지 않아서** 모델이 아예 다른 자리(few-shot 예시)에서 문체와 내용을 끌어왔다.

**조치**: `cluster_key`·`sample_merchants`가 둘 다 비면 LLM을 아예 부르지 않고 `app/ai/fallback.py`의 기존 `CLUSTER_NAMING` 템플릿(`_cluster_name()` — 대표 가맹점명 또는 "반복 소비 묶음")을 그대로 재사용한다. ACTION_PLAN의 `NO_MATCHING_SUGGESTION_REPLY`와 같은 이유로 이건 AI 장애가 아니라 정상적인 빈 입력 처리라 `fallback` 플래그는 세우지 않는다. 재실측 결과 3/3 정상("반복 소비 묶음"), LLM 호출 자체가 없어져 응답도 더 빨라졌다.

## 14. ANALYSIS 반말 유출 — 원인이 프롬프트 안이 아니라 사용자 입력 자체인 사례 (#66)

#66 검증 중 `ANALYSIS`를 반말로 질문하면("이번 달 배달 얼마나 썼어?") 답변도 반말이 섞이는 게 재현됐다(11/11). §12의 네 사례(INTRO·ACTION_PLAN·FINANCE_QA·ANALYSIS_NARRATE)는 전부 프롬프트 안의 **다른 텍스트 뭉치**(few-shot 예시, 긴 근거 JSON)가 `HAEYO_RULE`을 밀어낸 것이었는데, 이번엔 그런 텍스트가 없어도 샜다 — 원인이 시스템 프롬프트 쪽이 아니라 **`ctx.generate()`의 user 메시지로 그대로 들어가는 사용자 질문 자체의 말투**다. 모델이 시스템 프롬프트의 규칙보다 대화 상대(user 메시지)의 말투를 훨씬 강하게 흉내 낸다.

### 실측 단계별 결과

1. 규칙 없음(원래 `ANALYSIS_INSTRUCTION`): 11/11 반말
2. 추상적 규칙 한 줄 추가("사용자 질문이 반말이어도 답변은 항상 해요체로 쓰세요"): 6/6 그대로 반말 — 안 먹힘
3. 반말 어미 예시를 직접 명시하고 금지("사용자가 반말로 질문해도(예: "얼마 썼어?") 당신은 절대 그 말투를 따라 하지 않고 "~요"로 끝나는 문장만 씁니다(예: "96,000원이에요", "96,000원이야"는 금지)."): 13/14 정상 — 거의 다 잡힘

추상적 규칙과 구체적 금지 예시의 효과 차이가 뚜렷하다 — "반말이어도 해요체로"라는 문장은 모델에게 방향만 알려줄 뿐 무엇이 반말인지 구체적으로 못 박지 않아서, 사용자 메시지의 강한 신호를 못 이겼다. 실제 반말 표현("96,000원이야")을 금지 예시로 박아 넣자 효과가 났다.

**조치**: `ANALYSIS_INSTRUCTION`에 3번 문구를 반영했다. 범위 밖 질문 리다이렉트(#66의 다른 절반)는 이 변경과 무관하게 정상 동작한다(3/3 재확인). 100%는 아니므로(13/14), 잔여율은 §12의 FINANCE_QA·ANALYSIS_NARRATE와 같은 성격의 미해결 항목으로 남긴다 — 60문장 이상 표본 재검증은 아직 하지 않았다.

## 15. FINANCE_QA 임베딩 실패가 "AI 전체 장애"로 오분류된 사고 (#65)

server #73 항목 6 실측(2026-09-10)에서 FINANCE_QA가 로컬·운영 둘 다 임베딩 호출 실패(403 `model_not_found`) 때마다 검색 실패가 아니라 전체 장애로 잘못 분류돼 `fallback: true` 템플릿이 나갔다.

**원인**: `app/rag/retriever.py`의 `FinancialRetriever.search()`가 `self._embedder.embed([query])`를 호출하는 지점이, 뒤에 있는 asyncpg 전용 `try/except` **바깥**에 있었다. `embed()`가 던지는 `LLMUnavailableError`가 그대로 위로 새서 `app/agent/handlers/base.py`의 `call_tool()` 흡수 목록(`KeyError · SpringApiError · RetrieverUnavailableError · httpx.HTTPError · ValueError`)에도 안 걸리고, 결국 `SingleAgent.run`의 최상위 `except (LLMNotConfiguredError, LLMUnavailableError)`까지 올라가 검색 실패 하나가 "AI 전체 장애" 취급을 받았다.

여기에 임베딩 클라이언트 자체에도 타임아웃·재시도 정책이 없어(`AsyncOpenAI(api_key=...)`만 넘김) SDK 기본값(read 타임아웃 600초·재시도 2회)이 그대로 적용됐고, `SPRING_TIMEOUT_SECONDS`(10초)도 `ANALYSIS`·`ACTION_PLAN` 최악 경로(10 + LLM 6초 × 2 = 22초)에서 `AI_TIMEOUT_MS`(15초) 예산을 넘긴 상태였다.

**조치** (PR #70): ① `search()`가 `embed()` 호출을 감싸 `LLMUnavailableError`·`LLMNotConfiguredError`를 기존 `RetrieverUnavailableError`로 변환 — `call_tool()`이 흡수해 `ToolResult(success=False)`가 되고 근거없음 경로로 정상적으로 내려간다. ② `FinancialEmbedder`가 `LLMClient`와 같은 정책(`timeout=llm_timeout_seconds` · SDK `max_retries=0` + 자체 1회 재시도, 일시적 오류만 재시도)을 쓰도록 통일 — 대량 배치를 보내는 `scripts/ingest_financial_docs.py`에는 별도로 더 긴 타임아웃(60초)을 분리해 넘긴다. ③ `SPRING_TIMEOUT_SECONDS` 10 → 3초로 낮춰 `3 + 12 = 15`초로 예산을 정확히 맞춘다(여유 없음).

**운영 재실측** (2026-09-10, `api.clearpng.cloud`): `POST /chat/finance`에 근거 있는 질문("적금과 예금의 차이가 뭔가요?", "ETF가 뭔가요?")과 근거없는 질문을 섞어 보낸 결과 전부 `fallback: false`로 정상 응답했다 — 원래 원인이던 OpenAI 프로젝트의 임베딩 모델 접근 권한도 이 사이 별도로 해결됐다. 이 재실측 중 이 이슈와 무관한 별도 결함(§17 · #74)을 새로 발견했다.

## 16. 금융 RAG 유사도 하한 (#28)

`FinancialRetriever.search()`가 유사도 점수 하한 없이 항상 top-K를 반환해, 코퍼스에 관련 없는 청크만 있어도 항상 "근거 있음"으로 잡혔다. PR #27 발견사항 — 실시간 데이터성 질문에 용어 설명 청크의 예시 수치를 실제 답처럼 전달(발견사항 3), 최신성이 다른 여러 문서 중 낡은 정보가 뽑힘(발견사항 2 — 예금자보호 한도 5,000만원 vs 1억원)이 모두 이 지점에서 발생했다.

**실측** (PR #73, 로컬 격리 DB 741개 청크 · 실제 OpenAI 임베딩): 정답형 15문항의 top-1 점수는 0.283~0.708(평균 0.510), 근거없음형 14문항은 0.315~0.509(평균 0.408) — **두 그룹이 0.315~0.509 구간에서 겹쳐 단일 하한으로 완전히 분리되지 않는다.**

**채택값**: `FINANCIAL_RAG_MIN_SCORE = 0.48` — 문제 재현 질문("미국 기준금리 전망이 어때요?", score 0.473)을 거르는 가장 가까운 반올림 값이며, 근거 없는 확답을 줄이는 쪽을 우선한 선택이다. 적용 결과 정답형 10/15 근거 유지·5/15 빈 결과(false negative), 근거없음형 11/14 빈 결과·3/14 근거 잔존.

**예금자보호 한도의 특이 케이스**: 이 질문의 score(0.571)는 임계값을 넘어서 순수 점수 필터로는 걸러지지 않는다 — 배포 코퍼스 자체가 개정 전 금액을 담고 있어서다. 별도로 질문 키워드("예금자보호"+"한도"/"얼마"/"금액"/"까지") 기반 임시 차단 게이트를 추가했다 — 코퍼스를 최신 기준으로 재적재하면 제거해야 하는 **임시 정책**으로 명시해 뒀다.

**알려진 한계**: "복리란 무엇인가요?", "ETF" 등 일부 정답형 질문이 현재 표현에서 하한 미달(false negative)로 걸러진다. `score`가 `None`인 결과도 하한 미달과 동일하게 제거한다.

## 17. FINANCE_QA 근거없음 답변이 SYSTEM_PROMPT few-shot 예시를 베끼는 사고 (#74)

§15의 운영 재실측 중 근거없음형 질문에 답변이 이상하다는 게 드러났다 — 서로 다른 질문 4개(코스피 지수·환율 전망·삼성전자 주가·대출 한도)에 5회(반복 포함) 전부 같은 문장 **틀**로 답했다.

```
"확인된 근거가 없어 지금은 소비 흐름을 설명하기 어려워요."      (코스피 지수)
"확인된 근거가 없어 지금은 환율 전망을 설명하기 어려워요."      (환율 전망)
"확인된 근거가 없어 지금은 삼성전자 주가를 설명하기 어려워요."  (삼성전자 주가)
"확인된 근거가 없어 지금은 대출 한도를 설명하기 어려워요."      (대출 한도)
```

**원인**: `app/agent/prompt.py`의 공통 `SYSTEM_PROMPT` 응답 예시 중 하나("확인된 근거가 없어 지금은 소비 흐름을 설명하기 어려워요.")가 원래 ANALYSIS_NARRATE용으로 넣어둔 것인데, FINANCE_QA가 근거없음 상황을 만나면 자기 지시문(`NO_EVIDENCE_INSTRUCTION` — "확인할 수 없다는 문장 하나로만, 부연 설명 절대 금지")을 무시하고 이 예시 문장의 **구조**를 그대로 가져와 주제어만 바꿔 답했다. §13(CLUSTER_NAMING)과 원인이 같다 — 지시문이 있어도 모델이 프롬프트 안 다른 자리(few-shot 예시)에서 문체·형식을 끌어온다.

**조치** (PR #75): §13과 같은 해법 — 근거가 없으면 LLM을 아예 부르지 않고 `app/ai/fallback.py`의 새 상수 `FINANCE_QA_NO_EVIDENCE_REPLY`("확인할 수 있는 금융 자료를 찾지 못했어요. 다른 질문으로 다시 물어봐 주세요.")를 코드로 바로 반환한다. `NO_EVIDENCE_INSTRUCTION` 지시문 자체를 제거했다 — 지시문으로는 few-shot 유출을 못 막았다. `fallback`은 세우지 않는다(장애가 아니라 정상적인 근거없음 처리). LLM을 안 부르므로 투자 권유(FR-12-03·NFR-05) 위반 가능성도 이 경로에서 구조적으로 사라진다.

로컬 검증은 결정론적으로 통과한다(LLM 미호출). **운영 재배포 후 재실측(2026-09-10) — 같은 근거없음형 질문 2건 모두 새 고정 문장(`FINANCE_QA_NO_EVIDENCE_REPLY`)으로 응답, few-shot 유출 재현 없음.**

## 18. 금융 RAG를 BM25+벡터 하이브리드 검색으로 전환 (#78)

### 발견 — "적금이란"이 근거가 있는데도 차단됨

로컬 채팅 데모로 FINANCE_QA 정답형 질문을 반복 검증하던 중, "적금이란"이 #28의 유사도 하한(`FINANCIAL_RAG_MIN_SCORE = 0.48`)에 막혀 "확인할 수 없다"는 답이 나가는 걸 발견했다. 실측 점수는 **0.4776** — 임계값과 0.0024 차이다. 코퍼스에는 "정기적금"을 다루는 문단이 실제로 있었다.

### 원인 파악 — 두 갈래로 갈리는 실패

같은 방식으로 다른 정답형 질문(복리·단리·신용점수·신용카드/체크카드 차이·대출이자·자산관리·인플레이션)을 재현해 원인을 나눴다.

1. **벡터 임계값 경계 케이스** — 근거는 코퍼스에 있는데 벡터 유사도가 임계값 근처에서 갈린다(적금이 대표 사례). 짧고 사전적인 질문일수록 심하다 — 물음표 하나만 붙여도("적금이란" 0.4776 → "적금이란?" 0.4909, "예금이란"→"예금이란?"도 +0.024) 점수가 0.01~0.02 흔들려 통과·차단이 갈릴 정도다.
2. **코퍼스 커버리지 갭** — 개념을 직접 설명하는 문단 자체가 코퍼스에 없거나 희박하다. "인플레이션"은 단어 자체가 64회 등장하지만 정의 문단이 없고, "대출이자"는 이 표현이 코퍼스에 0회 등장한다. 이건 검색 알고리즘으로 못 고치는 문제라, 로컬 고등학교 금융 교과서를 신규 적재해 상당수 해결했다(신용카드·이자율·적금 커버리지 보강). 나머지는 별도 문서 적재(#62 계열) 후속 대상이다.

1번은 벡터 임베딩 하나만으로는 짧은 질의의 의미를 안정적으로 못 잡는다는, 검색 알고리즘 자체의 한계였다.

### 조치 — BM25 하이브리드 검색

`app/rag/keyword_index.py`를 신설해 Kiwi(`kiwipiepy`)로 형태소를 분석하고 명사류만 뽑아 `rank-bm25`로 BM25 인덱스를 인메모리에 짓는다(`financial_chunks` 스키마는 그대로 — server 소유 경계 유지). `FinancialRetriever`가 이 인덱스를 선택적으로 받아, 있으면 벡터 검색과 BM25 검색을 RRF(Reciprocal Rank Fusion)로 융합한다. 두 방식이 겹치지 않는 후보에서 동점이 나면 BM25 원점수로 타이브레이크한다.

재현 질문 8개(적금·복리·단리·신용점수·신용카드/체크카드·대출이자·자산관리·인플레이션) 전부 하이브리드 경로에서 정답 문단을 찾았다.

### 새로 발견한 문제 — 완전 무관 질문 오탐

하이브리드를 처음 붙였을 때 "김치찌개는 뭐임" 같은 완전 무관한 질문에 LLM이 레시피를 그대로 생성해 답하는 사고가 났다 — RRF는 순위만 매길 뿐 "이게 진짜 관련 있는지"는 안 걸러서, 완전 무관해도 뭔가는 top-K로 뽑혀 근거로 넘어갔다. FR-12-02·FR-12-03 위반이다.

BM25 원점수로 걸러보려 했지만 실패했다 — 코퍼스가 작으면(861개 Chunk) 절대값을 못 믿는다. "오늘"처럼 흔한 명사가 특정 Chunk에 몰려 있으면 완전 무관한 질문("오늘 날씨 어때")도 진짜 금융 질문("신용점수는 어떻게 정해져?")보다 BM25 점수가 높게 나왔다.

**최종 조치**: BM25로 살아난 후보도 자기 코사인 점수가 보조 하한(0.25)을 넘어야 통과하는 이중 게이트를 추가했다. 실측 8개 표본에서 진짜 관련 질문(코사인 0.28~0.40)과 완전 무관 질문(0.07~0.22)이 갈리는 지점이 이 값이다. 재검증 결과 정답형 8개는 그대로 유지되고, 완전 무관 질문(김치찌개·날씨·넷플릭스·파이썬 코딩)은 전부 다시 정상 차단됐다.

| 김치찌개는 뭐임 | 낮은 점수로 차단 | ✅ 여전히 차단(이중 게이트) |

`pytest` 274개 통과(신규 14개 포함).

### 리뷰에서 고친 것 (PR #79)

**1. BM25 0점 후보가 후보 목록을 채우던 문제.** `KeywordIndex.scores()`는 코퍼스
**전체**(861개)를 돌려준다. 그걸 그대로 정렬해 상위 15개를 자르면, 질문 용어가
실제로 맞은 게 1건뿐인 질문에서도 15개가 꽉 찬다 — 나머지 14개는 **테이블 적재
순서**로 뽑힌 무근거 Chunk고, RRF 융합에 들어가 순위 가점을 받는다. 벡터가 꼴찌로
민 Chunk가 1등으로 올라오는 경로였다. `rank()`가 0점을 걸러 내도록 고치고,
`_hybrid_search()`가 정렬을 따로 하지 않고 `rank()`를 쓰게 했다.

**2. 이중 게이트보다 `top_k` 절단이 먼저이던 문제.** 후보를 `top_k`로 자른 뒤
코사인 게이트를 걸면, 어차피 탈락할 BM25 후보가 자리를 먹어 **벡터 전용이었다면
나왔을 근거까지** 사라진다. RRF는 두 목록을 번갈아 세우므로 탈락 후보가 한 칸씩
끼어든다 — 재현 테스트에서 근거 5개가 2개로 줄었다. 절단을 게이트 뒤로 옮겨,
통과한 것만 세어 `top_k`에서 멈춘다.

**3. 벡터 후보를 두 번 읽던 문제.** `_SEARCH_SQL`로 이미 본문·점수를 읽어 놓고
`_BY_IDS_SQL`로 전부 다시 읽었다. 이제 BM25로만 올라온 후보만 추가로 읽고, 겹치면
질의를 아예 보내지 않는다(질의 1회 절약).

### 메모리 — `ai` 컨테이너가 62.8MiB에서 벗어난다 (07 §12)

07 §12-4 실측에서 `ai`는 **62.8 MiB**였고, `db`·`ai`에 `mem_limit`을 안 씌운 근거가
그 값이다. Kiwi 모델은 상주 메모리를 그만큼 차지하지 않는다 — 로컬 실측(861개
Chunk 합성 코퍼스, CPython 3.12) `ai` 프로세스 RSS:

| 시점 | 원본 PR | 조정 후 |
| --- | --- | --- |
| `app.main` import만 (하이브리드 미사용 기동 포함) | 416 MB | **108 MB** |
| + Kiwi 로드 + 861 Chunk 인덱스 구축 | 599 MB | **393 MB** |

조정은 두 가지다. (1) `Kiwi()`를 모듈 import 시점이 아니라 **첫 사용 때** 만든다 —
`retriever.py`가 `keyword_index`를 무조건 import하므로, 원본은 `DATABASE_URL`이
없거나 인덱스 구축이 실패해 **하이브리드를 안 쓰는 기동도** 416MB를 그대로 물었다.
(2) 오타 사전·다어절 사전을 끄고 `num_workers=1`로 만든다 — 오타 교정(`typos=`)을
쓰지 않고 명사 태그만 보므로 토큰화 결과는 기본 설정과 동일하다(재현 질문 17개로
확인). 대신 코퍼스 배치 토큰화가 병렬화되지 않아 기동이 약 3초 늘고, 전체 인덱스
구축은 약 5초다. 질의당 BM25는 0.5ms다.

그래도 393MB는 실측 62.8 MiB의 6배다. 호스트는 1.9 GiB에 used 1.1 GiB(07 §12-4)라
여유가 약 0.8 GiB뿐이므로, **배포 후 `docker stats`로 재실측하고 `ai`에도
`mem_limit`을 씌울지 판단해야 한다**. 상한이 없으면 호스트 OOM killer가 고르는데,
§12-3은 "그때 제일 큰 것은 대개 postgres"라고 적고 있다 — 이 변경으로 제일 큰 것이
`ai`가 될 수 있어 그 전제도 같이 바뀐다.

Docker 이미지는 약 335MB → 648MB로 늘었다(루트 볼륨 24GB 기준 여유 있음). 증가분의 대부분은
`kiwipiepy_model`이다 — sdist 88MB, 압축을 풀면 109MB(`cong.mdl` 76MB · `multi.dict` 12MB ·
`nounchr.mdl` 10MB)다. `load_multi_dict=False`로 껐어도 `multi.dict`는 이미지에 그대로 들어간다
— 껀 건 상주 메모리지 이미지 크기가 아니다.

이 패키지는 **PyPI에 휠이 하나도 없고 sdist만 있다.** C 소스가 없는 순수 데이터라 컴파일러는
필요 없지만(`python:3.12-slim`에서 그대로 빌드된다), `--only-binary=:all:`을 쓰는
CONTRIBUTING §7의 교차 해석 명령이 이것 때문에 실패한다 — lock은 Docker 방법으로만 뽑을 수
있다. §7에 경고를 달아 뒀다.

### 기동 시 인덱스 구축 실패는 재기동 전까지 계속된다 — 운영 절차

BM25 인덱스는 기동 시 한 번만 짓는다. 실패하면(타임아웃·`financial_chunks` 없음 등)
벡터 전용으로 계속 기동하고, **재기동 전까지 그 상태가 유지된다** — 조용히 #78("적금이란"이
0.4776으로 차단)이 되살아난 것과 같다.

**첫 기동(볼륨이 비었거나 DB를 새로 만든 직후) 레이스 하나가 특히 걸리기 쉽다.**
`deploy/docker-compose.yml`에서 `ai`·`server`는 둘 다 `db: service_healthy`에만
의존하고 서로의 순서는 안 정해져 있다. `db` healthy는 "접속은 받는다"까지고,
`financial_chunks` 테이블은 `server`의 Flyway `V8`이 만든다 — Spring 부팅+Flyway(수십 초)보다
`ai`(수 초)가 먼저 뜨면 `UndefinedTableError`로 하이브리드가 비활성인 채 남는다.
평소 재배포(`up -d ai`)에서는 테이블이 이미 있어 이 경로를 안 탄다.

**운영 절차**: `ai` 기동 로그에서 아래 줄이 보이면 원인과 함께 확인하고, 필요하면
`docker compose restart ai`로 다시 짓는다(원인이 첫 기동 레이스면 이 시점엔
`financial_chunks`가 이미 있어 재시도가 통과한다).

```
하이브리드 검색 비활성 — BM25 인덱스를 짓지 못했습니다: <예외 타입>: <메시지>
```

문서를 재적재했을 때도 마찬가지다 — 새 문서는 재기동 전까지 BM25 검색에 안 잡힌다
(벡터 검색에는 바로 반영된다).

## 19. ANALYSIS 자유 질문이 개별 거래를 못 보던 문제 — 카테고리별 거래 조회 추가 (#82)

### 문제

`ANALYSIS`는 카테고리 단위 **집계**(`byCategory`: 평균·월합계·주요시간대·판정)만 근거로
썼다. "편의점에서 뭐 샀어?"처럼 카테고리 단위 개별 내역을 물으면 답을 못 했고,
"홈마트에서 결제한 내역이 있어?"처럼 아예 안 보는 가맹점을 물으면 모델이
**단정적으로** "확인되지 않아요"라고 답했다 — 가맹점 데이터를 받은 적이 없는데도
"찾아봤는데 없다"는 어조라 신뢰 문제였다.

### 원인

`ToolName.TRANSACTION`(`app/tools/transaction_tool.py`)이 Tool Registry에
등록은 돼 있었지만(`app/agent/tool_registry.py:63`) 어떤 Task Handler도 부르지
않았다 — `ANALYSIS`가 LLM에 넘기는 필드는 `_PROMPT_FIELDS = (analysisYearMonth,
byVerdict, byCategory)` 셋뿐이고 셋 다 카테고리 집계라 가맹점명은 어디에도 없었다.

### 조치

질문 문장에 `byCategory`의 카테고리명이 그대로 들어 있으면(`_matched_category`)
`TRANSACTION` Tool을 그 `category` 필터로 한 번 더 불러 거래 목록(가맹점·날짜·금액)을
프롬프트에 얹는다. 카테고리는 고정 taxonomy가 아니라 카드사 CSV 원본 문자열이라
(server `TransactionFileParser`) 별도 사전을 안 두고, **이번 집계에 실제로 존재하는
카테고리명만** 후보로 삼는다 — 존재하지 않는 카테고리를 지어내 조회하지 않는다.
`number_guard`의 `known_numbers()`는 항목 리스트의 숫자 필드를 전부 훑는 범용
구현이라, 거래 목록을 세 번째 `groups` 원소로만 추가하면 거래 금액도 자동으로
"알려진 값"이 된다 — 별도 특수 처리가 필요 없었다.

**가맹점명("홈마트") 검색은 범위 밖이다.** `GET /transactions`에 가맹점 검색
필터가 없다(`from`·`to`·`category`·`size`뿐) — 계약 변경이 필요해 별도 이슈로
남긴다.

### AI → Spring 예산 영향

카테고리가 매칭되면 한 요청에서 Spring을 2회(집계 + 거래 조회) 부른다.
`AGENTS.md`의 "Spring을 여러 번 부르는 코드를 넣으면 이 표(05 §3 타임아웃 예산)를
먼저 고친다"는 규칙에 따라 05 §3에 새 행을 추가했다(01 v2.44 E-118). 최악
`3초×2(Spring) + 6초×2(LLM 재시도) = 18초`로 `AI_TIMEOUT_MS` 15초 예산을 넘길 수
있지만, 이건 두 Spring 호출과 LLM 재시도가 동시에 전부 실패해야 하는 케이스라
E-116과 같은 성격의 이론상 초과로 문서에만 남긴다 — 실제로 터지면 후속 이슈로
다룬다(코드로 미리 막지 않기로 했다).
